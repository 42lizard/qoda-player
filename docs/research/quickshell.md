# Quickshell integration and lifecycle evidence

Research date: 2026-10-25. Planning evidence for [Establish Quickshell integration and lifecycle options](https://github.com/42lizard/qoda-player/issues/4). No production architecture is selected here.

## Findings

Quickshell has the window, IPC, process and Qt Quick mechanisms needed for the proposed interface. It does not supply a Plex provider, mpv wrapper or a documented MPRIS player-service exporter. Those responsibilities need application code or a companion process; feasibility is different from an implemented integration. The [official overview](https://quickshell.org/about/) describes Quickshell as a Qt Quick/QML toolkit with process, socket, file and desktop-service integrations. The built-in [Mpris singleton](https://quickshell.org/docs/v0.3.0/types/Quickshell.Services.Mpris/Mpris/) lists connected players rather than registering this application as a player.

The local package database reports `quickshell 0.3.2.r7.g2b4501a-1`, `qt6-base 6.12.0-3`, `qt6-declarative 6.12.0-2`, `qt6-wayland 6.12.0-1`, and `mpv 1:0.41.0-6`. Evidence: read-only `pacman -Q quickshell qt6-base qt6-declarative qt6-wayland mpv` on the research date. This is a development-host snapshot, not a supported-version declaration. Upstream's [changelog](https://quickshell.org/changelog/) lists 0.3.2, including Qt 6.12 support; the [Arch Extra package](https://archlinux.org/packages/extra/x86_64/quickshell/) is 0.3.2-1. The machine has a development revision beyond that package version. The type references below use the published 0.3.0 documentation baseline; verify behavior against the eventual supported build.

## Windows, focus and invocation

- A full browser can use [FloatingWindow](https://quickshell.org/docs/v0.3.0/types/Quickshell/FloatingWindow/), documented as a normal operating-system toplevel, with title, size bounds, maximize/minimize/fullscreen and interactive move/resize support. Its name does not mean Hyprland will exempt it from tiling; compositor policy remains a separate integration question.
- A compact edge-attached panel can use [PanelWindow](https://quickshell.org/docs/v0.3.0/types/Quickshell/PanelWindow/). Anchors, exclusion mode and reserved area are explicit choices. On Wayland, layering and keyboard focus map to [WlrLayershell](https://quickshell.org/docs/v0.3.0/types/Quickshell.Wayland/WlrLayershell/). A full browser need not be a layer surface merely because its compact companion is one.
- Layer-shell input must be designed intentionally. [WlrKeyboardFocus](https://quickshell.org/docs/v0.3.0/types/Quickshell.Wayland/WlrKeyboardFocus/) provides None, OnDemand and Exclusive modes. Search focus, Escape behavior, focus restoration and coexistence with other overlays require a live Hyprland prototype; documented modes do not guarantee the desired user experience.
- [IpcHandler](https://quickshell.org/docs/v0.3.0/types/Quickshell.Io/IpcHandler/) exposes explicitly typed functions/properties through `qs ipc`. This is a supported route for a launch/toggle command. Local `quickshell --help` confirms named configuration selection (`-c`), path selection (`-p`), and `--no-duplicate`. Local `quickshell ipc --help` confirms config/instance selection and call/property/signal operations. A launcher still needs an agreed start-if-absent/toggle-if-present contract; the flags alone do not implement it.
- [GlobalShortcut](https://quickshell.org/docs/v0.3.0/types/Quickshell.Hyprland/GlobalShortcut/) is an alternative for a running instance, using Hyprland's own protocol and compositor binding. It does not launch an absent application. The documentation warns of collisions between duplicate app-id/name registrations across instances. A unique application identity and process-uniqueness policy are therefore design inputs.

## Hidden UI, reloads and playback lifetime

[QsWindow.visible](https://quickshell.org/docs/v0.3.0/types/Quickshell/QsWindow/) controls showing/hiding; hiding does not emit the `closed` signal. [Quickshell.lastWindowClosed](https://quickshell.org/docs/v0.3.0/types/Quickshell/Quickshell/) documents an explicit `Qt.quit()` handler if an application wants last-window close to exit. Inference: keeping the process and playback owner alive independently of visible windows can satisfy hidden-UI playback. This does not establish crash or reload continuity.

Hot reload is a separate boundary. [Reloadable](https://quickshell.org/docs/v0.3.0/types/Quickshell/Reloadable/) transfers selected state for supported object types; it is not blanket persistence for arbitrary QObjects or a native audio engine. The [Process header](https://raw.githubusercontent.com/quickshell-mirror/quickshell/master/src/io/process.hpp) explicitly says ordinary children are killed with Quickshell or configuration reload and points to `startDetached()` to avoid that coupling. The [destructor implementation](https://raw.githubusercontent.com/quickshell-mirror/quickshell/master/src/io/process.cpp) kills its running QProcess. A root-owned Process outlives hidden windows, but not its own destruction. Detached playback requires explicit discovery, reconnection and shutdown ownership. Neither detaching nor reloadable UI state saves the queue durably.

Quickshell exposes per-shell cache/data/state directories; its [changelog](https://quickshell.org/changelog/) notes that shell identity changes can move the default directory identity. An application-specific stable state location or explicit shell identity must be considered when deciding persistence and installation behavior. This is a planning constraint, not a recommendation to alter the current desktop.

## Provider access, models and artwork

Qt QML's [XMLHttpRequest](https://doc.qt.io/qt-6/qml-qtqml-xmlhttprequest.html) supports asynchronous HTTP, headers and response handling and does not enforce browser same-origin restrictions. Thus direct QML provider requests are technically possible; a browser CORS workaround is not inherently necessary. Token policy, cancellation, retry, schema adaptation and concurrency are application responsibilities. Large JSON parsing/model updates still need performance measurement rather than assuming asynchronous transport makes all work nonblocking.

[ListView](https://doc.qt.io/qt-6/qml-qtquick-listview.html) instantiates delegates for the visible region plus configured buffering and can reuse delegates. It accepts QML or native models. [QAbstractItemModel](https://doc.qt.io/qt-6/qabstractitemmodel.html) supports incremental loading through `canFetchMore`/`fetchMore`; model APIs belong to the model's thread, and worker results must be queued back to the GUI thread. Inference: large Plex libraries need bounded pages, stable item identities and incremental updates. View virtualization does not itself bound metadata loaded into memory. Replacing a large JS array for every update should not be assumed adequate without a representative-size benchmark.

[Image](https://doc.qt.io/qt-6/qml-qtquick-image.html) supports URL sources, asynchronous loading, requested source size and caching, but its documented QML properties do not expose per-request authorization headers. Do not assume Plex artwork can simply share the provider's HTTP header setup. [QQmlNetworkAccessManagerFactory](https://doc.qt.io/qt-6/qqmlnetworkaccessmanagerfactory.html) lets a host customize network managers and caching; that is a C++ host API, not proof of a ready-made QML switch in Quickshell. A local artwork cache or image provider is another possible boundary. Authenticated artwork, redacted URLs, persistent cache limits and stale-data rules remain design/prototype questions.

## Playback and desktop media controls

The [mpv embedding guidance](https://mpv.io/manual/master/#embedding-into-other-programs-libmpv) supports both controlling an external process through JSON IPC and using libmpv. Terminal text is not a stable control interface. Quickshell's [Socket](https://quickshell.org/docs/v0.3.0/types/Quickshell.Io/Socket/) can connect to a Unix socket, write strings and flush, so JSON IPC is a plausible direct integration. It still needs framing, request correlation, event handling and reconnection. mpv's IPC is local and unauthenticated: socket placement and permissions must be part of the application contract.

The [libmpv client header](https://raw.githubusercontent.com/mpv-player/mpv/master/include/mpv/client.h) supplies commands, properties and events and explains integration with a GUI event loop using wakeup callbacks and nonblocking event polling. It warns synchronous calls can wait indefinitely on playback-core work. Inference: a Qt bridge must use asynchronous commands and safe event delivery rather than blocking the QML/GUI thread. No QML-native libmpv binding was established in the official Quickshell type surface inspected here.

Quickshell's built-in MPRIS integration is a controller of existing services. Qoda must separately export a player service from its authoritative playback/session owner. The [MPRIS specification](https://specifications.freedesktop.org/mpris/latest/) requires a bus name under `org.mpris.MediaPlayer2`, `/org/mpris/MediaPlayer2`, root/player interfaces and state-change notifications; tracklist and playlists are optional interfaces. [Qt D-Bus](https://doc.qt.io/qt-6/qtdbus-index.html) is a supported C++ mechanism to implement that service, either in a native module or a companion process. Native media keys can then control Qoda through the desktop's MPRIS consumer; Quickshell discovering other players does not provide this automatically.

## Feasible topology families, without selecting one

| Family | Evidence-backed mechanism | Tradeoff to decide |
| --- | --- | --- |
| Quickshell owns application state; mpv is a child process | QML HTTP/models, Process, Socket, mpv JSON IPC | Low native integration burden, but Quickshell reload/crash couples state and ordinary child lifetime; MPRIS export still needs an implementation. |
| Quickshell loads a native QML module owning libmpv and provider/storage code | Qt registered QObject types, shared QML module, libmpv C API | Rich native models and direct events; native failure/lifecycle shares the UI process and deployment needs compiled artifacts. |
| Quickshell renders state from a companion backend owning playback/session/provider/storage | Unix-socket transport or a purpose-built Qt bridge; backend libmpv or mpv IPC; backend MPRIS | Independent playback lifetime and one media-service owner; IPC protocol, activation, reconnect and package lifecycle become explicit contracts. |

Qt supports [registering QObject types for QML](https://doc.qt.io/qt-6/qtqml-cppintegration-definetypes.html) and building shared modules with [qt_add_qml_module](https://doc.qt.io/qt-6/qt-add-qml-module.html). These establish the native extension route in Qt, not a stable Quickshell-internal extension ABI. Prefer public Qt APIs if that family is chosen. A minimal import/construct/event-delivery smoke prototype is still needed on the selected Quickshell package before committing to it.

## Packaging constraints

The upstream [build instructions](https://github.com/quickshell-mirror/quickshell/blob/master/BUILD.md) require at least Qt 6.6 and explicitly warn that Quickshell's private Qt API use requires rebuilding against every Qt release to avoid ABI crashes. They identify optional features including sockets, Wayland/layer shell, MPRIS and Hyprland shortcuts. A supported package must include the features the selected architecture uses. The [Arch package dependencies](https://archlinux.org/packages/extra/x86_64/quickshell/) provide a concrete distribution baseline; they do not guarantee arbitrary old/new local package combinations. Shipping QML separately does not remove the host ABI constraint. A companion process reduces direct dependence on Quickshell internals but does not remove its own dependencies or IPC compatibility obligations.

## Evidence gaps and decisions now made sharp

1. Does playback need to survive UI reload or crash, or only hiding/closing windows? The current requirement settles hiding only. Choose the authoritative session owner before specifying reconnect behavior.
2. Should the full browser be a compositor-managed toplevel and the compact view a layer panel, or should both use normal windows? Prototype focus, keyboard traversal, toggle and Escape on the target Hyprland version and multiple monitors.
3. Which runtime family owns MPRIS, queue and durable state? Avoid multiple independently writable playback/queue authorities.
4. If a native module is considered, can a minimal public-Qt plugin import successfully, receive libmpv events without blocking, and shut down cleanly across hide/reload/exit on the supported host build? Documentation establishes a route, not completion of that validation.
5. Which authenticated artwork path and paginated model perform acceptably with a representative large library? Define a measurable size/latency target before a performance prototype.
6. What version/feature matrix, stable app/shell identity and update policy will be supported? Local packages are observations only; no desktop was changed and no UI or audio prototype was executed in this research ticket.

All topology comparisons and suggested follow-up experiments are inferences from the linked mechanisms. They do not resolve product or architecture tickets, promise hardware audio properties, or select an implementation language.
